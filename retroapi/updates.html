What's New in 0.2.3

Sharper tools that finally work on vanilla blocks, tags for items, layered sprites and facing blocks with no boilerplate, cast-free access, and a clean StationAPI hand-off.

This chapter is a changelog you can read like a chapter. Everything here is new since 0.2.2, and every claim below is exercised by the test mod's headless self-checks, so it is behavior you can rely on, not just intention. The older chapters still describe the shape of the API; this one collects what changed.

Custom tools now work on vanilla blocks

The headline fix. Before, a plain Item told to be a pickaxe (the Ruby Pick from Chapter 18) only mined modded blocks that had been tagged mineable/pickaxe; on vanilla stone or iron ore it did nothing, because no vanilla block was in any RetroAPI tag. RetroAPI now ships the beta-accurate default membership for every vanilla block, generated from beta's own MinecraftPickaxe/Axe/Shovel tables and harvest levels:

TagVanilla blocks (beta-accurate)
mineable/pickaxestone, cobblestone, ores, metal/diamond/lapis blocks, obsidian, furnace, rails, …
mineable/axeplanks, logs, bookshelf, chest, crafting table, fences, pumpkins, …
mineable/shoveldirt, grass, sand, gravel, clay, snow, farmland, soul sand
needs_stone_tooliron ore/block, lapis ore/block
needs_iron_toolgold ore/block, diamond ore/block, redstone ore
needs_diamond_toolobsidian

So the exact Ruby Pick from Chapter 18 now mines vanilla iron ore, at iron-tier speed, with no extra work. A custom iron pick reaches iron ore and lapis; a custom diamond pick reaches obsidian; and so on, matching vanilla to the block.

Decoupled semantics (matches modern Minecraft). A mineable/<tool> tag now grants speed only. Whether a block needs a tool to drop comes from its material (beta's stone/metal rule) or a needs_<tier>_tool tag. That is why axes and shovels can be fast on hand-breakable logs and dirt without those blocks suddenly requiring a tool to drop. If you previously relied on .mineable(...) alone to gate drops on a hand-breakable material, give that block a stone/metal material or a needs_<tier>_tool tag instead.

Tools can be more than one kind, and pick their tier at runtime

.tool(...) now takes several kinds, so one item can be a pickaxe and an axe (a paxel), mining everything in both tags:

a multi-kind tool
PAXEL = (Item) RetroItemAccess.create()
    .maxStackSize(1)
    .tool(RetroTool.PICKAXE, RetroTool.AXE)   // mines mineable/pickaxe AND mineable/axe
    .tier(RetroToolTier.IRON)
    .register(id("paxel"));

And .tier(...) now accepts a lambda over the actual ItemStack, so a tool's tier can change at runtime, from its damage, its NBT, whatever you like:

a tier that rides the stack
DYNAMIC_TOOL = (Item) RetroItemAccess.create()
    .maxStackSize(1)
    .tool(RetroTool.PICKAXE)
    // undamaged = diamond-tier, worn = iron-tier; consulted on every harvest
    .tier(stack -> stack.getDamage() == 0 ? RetroToolTier.DIAMOND : RetroToolTier.IRON)
    .register(id("dynamic_tool"));

A declared plain-Item tool now also mines at its tier's speed (wood 2×, stone 4×, iron 6×, diamond 8×), instead of a flat token boost, so .tier(IRON) feels like an iron tool. And RetroTool.SHEARS was added to match StationAPI's tool set.

Tags for items, and arbitrary tags at runtime

RetroTags.addToTag used to be blocks-only. Now it takes items too, both block and item tags are queryable, and any tag can be edited at runtime (StationAPI's tags are frozen from resources; RetroAPI's are live):

arbitrary item + block tagging, at run time
import com.periut.retroapi.tag.RetroTagKey;
import com.periut.retroapi.tag.RetroTags;

RetroTagKey GEMS = RetroTagKey.item("mymod/gems");
RetroTags.addToTag(GEMS, RUBY, SAPPHIRE);        // items
RetroTags.addToTag(RetroTagKey.block("mymod/bouncy"), SLIME_BLOCK);

boolean isGem = RetroTags.isIn(RUBY, GEMS);      // true, immediately
Set<Item> gems = RetroTags.itemsIn(GEMS);
RetroTags.removeFromTag(GEMS, SAPPHIRE);         // also live

Item tag data files load too, from the same layouts as blocks, including StationAPI's data/<ns>/stationapi/tags/items/<p>.json. Vanilla item names resolve through a flattening map (minecraft:iron_ingot, minecraft:cod/raw_fish, …).

Layered item sprites with no model JSON

Stacking sprites (the candied-apple trick from Chapter 5) no longer needs a model or definition JSON. Give the base and overlays straight to the builder:

a glinting apple, entirely in code
CANDIED_APPLE = RetroItemAccess.create()
    .maxStackSize(16)
    // base + overlays flattened onto one atlas slot; vanilla or modded, any mix
    .layers(id("minecraft", "apple"), id("sugar_sparkle"))
    .food(4)
    .register(id("candied_apple"));

// or stack onto an existing .texture(...) with .overlay(...):
RetroItemAccess.create().texture(id("wand")).overlay(id("wand_glow")).register(id("wand"));

A model JSON, if one exists, still wins, so nothing you already ship changes.

Facing blocks with no onPlaced

The freezer from Chapter 17 needed a custom Facing enum and an onPlaced override. Both are now built in. RetroFacing is a ready-made four-direction property, and .facing() declares it and turns the block toward the placer on placement:

furnace-like rotation, one call
FREEZER = RetroBlockAccess.of(new FreezerBlock(RetroBlockAccess.allocateId()))
    .sounds(Block.STONE_SOUND_GROUP)
    .strength(3.5f)
    .facing()   // declares RetroFacing.PROPERTY, orients to the placer, aims the icon south
    .register(id("freezer"));

You still supply the look with a blockstate JSON that y-rotates one orientable-style model per facing= value (exactly the Chapter 17 JSON), and a BlockWithEntity still overrides getRenderType() to honor it. What is gone is the hand-written enum and the onPlaced math. A fully code-generated .sided(top, side, front) that also builds the model is the next step on this same foundation.

No more casting, and constructor factories

Block and Item now carry the RetroAPI access interfaces through interface injection, so a mod that depends on RetroAPI (via modImplementation) calls RetroAPI methods on them with no cast:

no (RetroBlockAccess) cast needed in a consuming mod
Block b = Block.STONE;
if (b.isAlwaysDrops()) { ... }        // was: ((RetroBlockAccess) b).isAlwaysDrops()

And you can wrap a subclass by its constructor, skipping the id boilerplate:

of(Constructor::new)
COUNTER = RetroBlockAccess.of(CounterBlock::new)          // CounterBlock(int id)
    .sounds(Block.STONE_SOUND_GROUP).register(id("counter"));

// with a Material arg:
RetroBlockAccess.of(MyBlock::new, Material.STONE).register(id("my_block"));

// items too (AUTO_ID is resolved inside the constructor):
RetroItemAccess.of(WandItem::new).texture(id("wand")).register(id("wand"));

A reminder when a name is auto-generated

Unnamed blocks and items still get a pretty display name for free, but the log now names which ones, so a missing lang entry is a visible reminder rather than a silent default:

client log
Using AUTO-GENERATED names for 2 unnamed block(s)/item(s) (add a lang entry to override):
  mymod:counter -> "Counter", mymod:gem -> "Gem"

StationAPI: a clean hand-off

RetroAPI reads StationAPI's exact tag layouts (data/<ns>/stationapi/tags/blocks|items/**.json) and matches its vanilla flattening names, so the same tag files work in both with no changes. When StationAPI is present, RetroAPI stands back from vanilla harvesting entirely, StationAPI already ships those tags and owns it, and RetroAPI's hooks only act on the modded blocks it tagged itself. The full comparison is in STATIONAPI_TAG_COMPAT.md in the source repo.

That is 0.2.3: the toolbelt from Chapter 18 finally bites everywhere it should, tags reach items, and the boilerplate around sprites, facing, and casts is gone.
