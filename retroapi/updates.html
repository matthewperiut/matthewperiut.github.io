What's New in 0.3.0

A door that opens at the right moment, the fix for recipes that "randomly don't exist", particles, world features, tools built from numbers instead of materials, and a pile of things that no longer need a custom renderer.

This chapter is a changelog you can read like a chapter. Everything here is new since 0.2.4. The older chapters describe the shape of the API; this one collects what changed and, where it matters, why the old behaviour was wrong.

The retroapi entrypoint

Mods now register through their own door, which RetroAPI opens at exactly one moment:

src/main/resources/fabric.mod.json
	"entrypoints": {
		"retroapi":        [ "com.example.example_mod.ExampleMod" ],
		"retroapi-client": [ "com.example.example_mod.ExampleModClient" ],
		"retroapi-server": [ "com.example.example_mod.ExampleModServer" ]
	},

Implement RetroModInitializer.initRetro() (plus RetroClientModInitializer / RetroServerModInitializer for the sided halves). The loader runs init in an unspecified order, so a mod could initialize before RetroAPI had finished building the platform it was calling into; that is the root of the "sometimes my content is just missing" family of bugs. Content registered from initRetro() is ordered after the registries, tag defaults and lang files are ready, before RetroAPI's own registration events, before recipes are sorted, and before any world assigns ids. It also fires identically with and without StationAPI, which RetroAPI's registration events do not. Full story in Chapter 2; migration is three lines of JSON and one method rename.

Recipes that vanished, and the id remap behind them

A recipe is an ItemStack, and an ItemStack stores a numeric id. Mods register during init, when ids are still provisional; the real ones arrive when a world's saved id map (or a server's table) is applied. Every stack built beforehand kept the old number, so recipes stayed in the list, count and all, and silently stopped matching, unless this session's provisional ids happened to match, which is exactly why relaunching sometimes "fixed" it.

RetroAPI now sweeps everything it knows about after an id change: crafting recipes (its own and vanilla's), smelting inputs and outputs, fuel entries and achievement icons. Mods that cache stacks or raw ids themselves can join the sweep:

for mod-held stacks
IdRemapCallback.EVENT.register(remap -> {
    remap.fix(ExampleMod.STARTER_KIT);
    ExampleMod.magicItemId = remap.map(ExampleMod.magicItemId);
});

The crafting list is also re-sorted at that point, so recipes registered late still land in vanilla's shaped-before-shapeless order.

Tools and blocks now agree with each other

Two halves of one long-standing trap, both closed:

  • Blocks without tags get sensible defaults. A block that declares no mineable tag is inferred from its material (stone/metal → pickaxe, wood → axe, soil/sand/snow → shovel, leaves → shears/sword/hoe, wool/cobweb → shears). Beta answers "is this tool effective?" from hardcoded block lists inside each vanilla tool, which no modded block is in, so a modded stone-material block used to drop nothing for any tool.
  • Declared tools answer vanilla's own question. RetroAPI now hooks beta's isSuitableFor, so a custom tool that subclasses nothing is recognised by every vanilla path: drops, breaking speed, and the correct-tool check.

And a tool no longer needs a ToolMaterial (an enum a mod cannot extend). Give the numbers instead, on any item:

a tool with no material
DRILL = RetroItemAccess.create()
    .tool(RetroTool.PICKAXE, RetroTool.SHOVEL)
    .tier(RetroToolTier.IRON)
    .miningSpeed(9.0F).attackDamage(4).durability(750)
    .handheld().texture(id("drill")).register(id("drill"));

Tiers can now also depend on what is being mined: .tier((stack, block) -> …), consulted per harvest. Chapter 18.

Particles

b1.7.3 resolves particle names in a hardcoded if chain, so there was no way to add one. There is now a registry, a ready-made sprite particle, and, because the protocol has no particle packet and vanilla's server-side listener is an empty method, a bridge so server-spawned particles actually reach players:

register on the client, spawn from anywhere
RetroParticleRegistry.register(ExampleMod.SPARK, (world, x, y, z, vx, vy, vz) ->
    new RetroSpriteParticle(world, x, y, z, vx, vy, vz, ExampleMod.SPARK_TEXTURE)
        .lifetime(24).scale(0.9F).gravity(0.02F).tint(0xFFD070).shrink());

RetroParticles.spawnCloud(world, ExampleMod.SPARK, x + 0.5, y + 1.0, z + 0.5, 12, 0.25);

The whole chapter is new: Chapter 22.

World features without a mixin

Ore generation used to mean mixin-ing vanilla's chunk generator, with no rarity knob, no metadata, and nothing but stone replaceable. Register instead:

initRetro()
RetroFeatures.ore(RUBY_ORE).size(6).count(8).heightRange(4, 32).register();
RetroFeatures.ore(STONE_TYPES).meta(2).size(48).count(3).rarity(3)
    .heightRange(0, 96).replace(Block.STONE).register();
RetroFeatures.custom((world, random, x, y, z) -> { … }).count(1).rarity(64).register();

The hook sits on the chunk cache, so it covers vanilla dimensions, modded dimensions and custom generators alike, and the decoration random is seeded exactly like vanilla's, so seeds still reproduce. Chapter 20.

Six-way facing, directions with opinions, and a position type

  • .facingAll() for blocks that also point up and down; RetroDirection with opposite(), rotateLeft()/rotateRight(), vector(), face(), nearest(dx, dy, dz), and fromPlacer(entity).
  • RetroFacing gained the same helpers, so horizontal blocks don't have to convert.
  • RetroVec3i: an immutable block position with add/subtract/multiply/offset(direction), distances, and world access (blockId, state, setBlock, blockEntity).
  • Fixed: .states(...) after .facing() used to drop the facing property. They merge in either order now.

Multiblocks, and a pass that runs when the world is real

RetroMultiblock takes a shape as ASCII layers plus a legend, matches it in one rotation or all four, and hands back every matched position (by character, if you like). BlockEntityLoadedCallback fires once per block entity on its first tick, the earliest moment at which NBT is read and the world exists, replacing the hand-rolled "have I initialised yet?" boolean. Chapter 23.

Blocks: less renderer, more builder

  • .sided(top, side, front[, bottom]), .column(top, side) and .textures(bottom, top, north, south, west, east), per-face textures in code, following the facing state where there is one.
  • .tint(provider), per-position colour for plain code-textured blocks, not just model faces with a tintindex.
  • .overlay(...), extra render passes over the same block, each with its own tint (the grass-edge trick, generalised).
  • .tag(...), .needsTool(tier) and .unbreakable(), tags and bedrock-hardness without a subclass.
  • RetroCharProperty, characters as state values, no 'a' + n arithmetic.
  • Fixed: breaking and replacing a block with more than 16 states no longer truncates it to the metadata nibble.

For custom renderers

BlockRenderContext gained the primitives a connected-texture or decal renderer actually needs: spriteOverride, flipTexture, faceRotation, renderAllFaces, and, for full control, renderFaceUv(face, sprite, u0, v0, u1, v1, flip) plus renderFaceCorner(...). Drawing a quarter of a sprite, mirrored, no longer means resizing the block's bounding box six times per corner or shipping pre-flipped copies of every texture.

Interface injection, actually injected

Block and Item have advertised RetroAPI's access interfaces since 0.2.3, so that block.strength(...) needs no cast. On the Ornithe build, the one the maven and these docs point at, it never took effect: the declaration was keyed with babric's older intermediary names, and Loom matches those keys against the consumer's namespace, which is calamus gen2 here. Both namespaces are declared now, so cast-free access works on either toolchain.
