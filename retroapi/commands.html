Commands

Brigadier, in b1.7.3. The same tree, the same builders, the same argument types you already write against on modern.

RetroAPI 0.4.0 embeds a Brigadier fork and a command system built on it. If you have written a command for modern Minecraft, the code below will look like something you have already written, because it is: literal, argument, .then, .executes, .requires, .suggests all mean what they mean there.

Beta has no integrated server. Singleplayer is the client simulating the world itself, so a "server-side" command in singleplayer runs on the client. That is what RegistrationEnvironment is for, and it is the one thing about this API that has no modern counterpart.

Registering a command

Register a callback during your mod's initialisation. It runs every time the tree is built, which is once per world on a client and once at start-up on a dedicated server.

src/main/java/com/example/example_mod/ExampleMod.java, in initRetro()
CommandRegistrationCallback.register((dispatcher, environment) ->
	dispatcher.register(literal("hello")
		.executes(context -> {
			context.getSource().sendFeedback(Text.literal("Hello, world"));
			return Command.SINGLE_SUCCESS;
		})));

The static helpers come from RetroCommandManager, so a file of commands usually starts with these two imports and reads exactly like modern's:

import static com.periut.retroapi.commands.RetroCommandManager.argument;
import static com.periut.retroapi.commands.RetroCommandManager.literal;

The source

RetroCommandSource is modern's CommandSourceStack: who ran the command, where from, and how much they are allowed to do.

MethodWhat it gives you
sendFeedback(Text)output to whoever ran it, chat or console
sendError(Text)the same, styled as a failure
getPlayer() / getPlayerOrThrow()the player, or a clean "you must be a player" error
getEntity() / getEntityOrThrow()the entity, which for a command block is none
getWorld()the world the command acts on
getPosition()where it ran, which is what ~ ~ ~ is relative to
hasPermissionLevel(int)LEVEL_ALL 0, LEVEL_MODERATOR 2, LEVEL_OWNER 4

Permissions

.requires(...) gates a whole branch, exactly as on modern. A source that fails the test does not merely get refused: the branch is left out of the tree it is sent, so the command does not appear in its completions at all.

dispatcher.register(literal("smite")
	.requires(source -> source.hasPermissionLevel(RetroCommandSource.LEVEL_MODERATOR))
	.executes(context -> { /* ... */ return Command.SINGLE_SUCCESS; }));

Arguments

Brigadier's own types are all here (IntegerArgumentType, StringArgumentType, BoolArgumentType, …) plus the game-specific ones, which live in com.periut.retroapi.commands.argument.

TypeAcceptsRead it back with
entity() / entities()a name, or a selector: @p @a @r @e @s with [distance=..8,limit=3,type=Pig]getEntity / getEntities
player() / players()the same, restricted to playersgetPlayer / getPlayers
blockPos()10 64 -30, ~ ~2 ~, ^ ^ ^3getBlockPos
vec3()the same, not rounded to the blockgetVec3
block()stone, minecraft:wool:14, 35:14getBlock
item()the same for items, with a stack sizegetItem
dimension()minecraft:overworld, a RetroAPI dimension, a StationAPI onegetDimension
gameMode()survival creative adventure spectator, their initials, or 0-3getGameMode
time()day, night, 1000t, 2dgetTime
message()the rest of the line, with selectors resolved inside itgetMessage
entitySummon()a registered entity idgetEntitySummon
dispatcher.register(literal("heal")
	.requires(source -> source.hasPermissionLevel(RetroCommandSource.LEVEL_MODERATOR))
	.then(argument("targets", players())
		.then(argument("amount", integer(1, 20))
			.executes(context -> {
				int amount = IntegerArgumentType.getInteger(context, "amount");
				for (PlayerEntity player : getPlayers(context, "targets")) {
					player.heal(amount);
				}
				return Command.SINGLE_SUCCESS;
			}))));

Suggestions

Every argument type above suggests its own values. For your own, hang .suggests(...) on the argument node and use the helpers in SuggestionHelper, which are modern's CommandSource.suggestMatching and friends.

.then(argument("colour", StringArgumentType.word())
	.suggests((context, builder) -> SuggestionHelper.suggestMatching(
		List.of("red", "green", "blue"), builder))
	.executes(context -> { /* ... */ return Command.SINGLE_SUCCESS; }))
HelperWhat it does
suggestMatching(Iterable<String>, builder)prefix match, case-insensitive
suggestMatching(…, builder, tooltips)the same, with a tooltip per entry
suggestIdentifiers(Iterable<String>, builder)namespaced ids: offers namespaces first, then matches on the path alone

Suggestions on a server come from the server. A client running RetroAPI is sent a copy of the tree it is allowed to use and asks the server for completions it cannot compute itself, such as who is online. On a vanilla server the local tree is used, which still colours the syntax.

Where a command runs

The second parameter of the callback is RegistrationEnvironment. DEDICATED is a real server; INTEGRATED is singleplayer, where the client is the world. Use it to leave out commands that make no sense with nobody else connected.

CommandRegistrationCallback.register((dispatcher, environment) -> {
	if (environment.isDedicated()) {
		dispatcher.register(literal("broadcast") /* ... */);
	}
});

Client-only commands

A command that never needs the server, such as one that changes a local setting, can be registered the same way and simply never sent anywhere: in singleplayer everything is client-side already, and on a server the client's own tree still parses it.
